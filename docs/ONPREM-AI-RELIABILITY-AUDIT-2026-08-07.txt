二、測試方法與判定範圍

測試 harness 走和產品相同的核心路徑：

- 同一套摘要 prompt、Zod schema、分卡 parser、來源 catalog 與 finalizer。
- 同一套 FHIR tools、資料範圍、地端 router、deep-mode agent loop。
- temperature=0；gpt-oss 才會送 reasoning_effort=low。
- 預設不保留完整 prompt 或完整回答，只記分數、錯誤類別、hash、token 與延遲。
- 只有使用 --include-output 的合成資料除錯 run 會留完整輸出；results 目錄已 gitignore。

自動檢查項目：

- JSON / 卡片是否可解析、必要欄位是否齊全。
- sources 與 timeline.ref 是否真的存在於 app 建立的來源 catalog。
- 藥名是否被翻譯、替換或憑空新增。
- 沒有藥物資料時是否虛構用藥。
- 未提供參考區間時是否自行補一般正常值。
- claim ICD 是否被錯當成確認診斷。
- X 光只有標題與日期時是否虛構肺炎、浸潤、胸水等判讀。
- Chat 工具選擇、參數、擷取結果與最後答案是否一致。
- 臺灣繁體中文、明確簡體字與 <tool_call> 等協定標記是否外洩。

限制：

- 這是工程穩定度與 grounding 自動測試，不是醫師對每一句臨床內容的人工 gold-standard review。
- 簡體檢查只使用不會與繁體共字混淆的明確字元，因此是保守下限，不是完整語言稽核。
- 多數模型矩陣是每案例 1 次；高風險案例另做 3 次或 10 次重複。
- 「目前 guideline」若模型沒有外部文獻搜尋工具，只能誠實說無法驗證最新版本，不能把訓練知識宣稱為最新。


三、主要失敗模式與實驗發現

1. 只加長 prompt 不夠

舊 prompt 常見問題：

- HbA1c 沒有 reference range，模型自行補 4.0–5.6、<5.7、>6.5 等一般數字。
- claim ICD E11.9 被當成已確診糖尿病。
- Exemestane (Aromasin) 被翻譯成錯誤藥名，曾出現「阿romasin」或完全不同藥物。
- 沒有 Medication source 時仍虛構 Captopril M1。

改善後 prompt 會把 clinical context 視為唯一病人事實來源，禁止翻譯／推測藥名、補正常值、把 claim 當確診，並明確要求臺灣繁體中文。

2. gpt-oss:20b 的 hidden reasoning

沒有 reasoning control 時，複雜自定義摘要曾耗時約 53 秒、輸出 token 7,508，但可見回答只有約 367 字；另一次逾時 120 秒。單純降低 max_tokens 或在 system 寫「Reasoning: low」仍可能回空答案。

對院內 OpenAI-compatible endpoint 實測後，request body 的 reasoning_effort="low" 才有效：相同案例約 4.6 秒、981 total tokens，並回傳完整答案。

此參數不能無差別送給所有模型：

- Gemma 可能回空 final。
- Nemotron 可能把英文 reasoning 暴露在使用者內容。

因此程式以實際 endpoint model id 判斷，只對 /^gpt-oss(?::|-)/i 送 reasoning_effort。

參考：
https://developers.openai.com/api/docs/models/gpt-oss-20b
https://openai.com/index/introducing-gpt-oss/

3. 小模型會在 tool arguments 自行加錯範圍

Nemotron 曾把「胸部 X 光」改成自行猜測的日期範圍，導致查不到實際 2025-05-18 的 Chest X-ray，之後錯誤回答沒有資料。

修正方式不是繼續擴大意圖詞彙表，而是：

- 使用者先明確選資料範圍。
- 地端模型在範圍內只拿到相關的精簡工具。
- 對可安全用空參數執行的 compact tools，由瀏覽器先執行，再讓模型只整理結果。
- 現在的 prefetch allowlist：getDataOverview、getHealthSummarySnapshot、getActiveMedicationList、getRecentVisits、queryImagingRecords。

這套 prefetch 只用於 custom / on-prem endpoint。Frontier 的 auto 模式不使用 router 縮減或強制工具，保留自主 tool selection。

4. 中英文 FHIR 名稱不一致

使用者問「胸部 X 光」，FHIR code.text 可能是 Chest X-ray。工具新增小而保守的 modality / anatomy alias，只做等價字面對應，不推論影像結果。

藥物工具原先只回 canonical English Sotalol，遺失來源 text「通舒錠」。現在同時回：

- medication：canonical coded label，例如 Sotalol。
- recordedName：來源中的原始名稱，例如 通舒錠。
- status：來源狀態。

模型被要求逐字重複兩欄，不得自行翻譯兩者關係、成分、用途或藥理分類。

5. Parsed JSON 不代表 grounded

小模型可能輸出合法 JSON，但 sources 寫了 catalog 不存在的 M1。正式版現在會在接受卡片前掃描所有 sources / ref：

- 任一不存在的來源鍵，該卡標為 GROUNDING_FAILED。
- 只重送失敗卡，不重送已成功卡。
- 初始批次最多自動重試 2 張卡，避免每次重傳完整病人 context。
- 若重試仍失敗，顯示卡片失敗，不把虛構內容渲染成真的病歷。

Finalizer 還會二次保護藥物卡：沒有有效 Medication source 的 regimen / change / reconciliation 會被丟棄；若所有引用列都被丟棄，無來源的 overview 也不保留。

6. 保守 partial parser 比再次重送更省 token

gemma4:26b 在腎功能案例會固定把 priorities JSON 的最後 segment 截壞，但前面的 headline 與 4 個 segment 完整且有合法來源。

新增 parser 只保留可獨立 JSON.parse、通過 SummarySegment schema 且後續通過來源鍵驗證的完整 segment；不修字、不猜遺失內容，少於 2 個完整 segment 就拒絕。修正前該案例 0/3；修正後 3/3，且每次只用 1 次 API。

五、建議的產品配置

1. 結構化摘要預設

優先候選：tvghbrain3.5、gpt-oss:120b、gemma4:31b。

- 若最重視目前院內既有部署與已完成 10/10 跨院回歸：tvghbrain3.5。
- 若要比較較大模型的內容品質：gpt-oss:120b。
- gpt-oss:20b 雖正確，但延遲不適合互動式預設。
- gemma4:26b 可作備援，但保留有限卡片 retry 與 partial parser。
- Nemotron 不建議開放此功能。

2. 自定義摘要

六模型目前都可用 grounded prompt。tvghbrain3.5、Gemma 31B／26B 延遲最低；gpt-oss:20b 必須保留 reasoning_effort=low 的 model-specific 設定。

3. Chat

優先候選：gemma4:31b、gemma4:26b；tvghbrain3.5 可用並保留 compact prefetch 與 timeout 監控。Nemotron 不建議。

4. Frontier 模型

不套用地端小模型的精簡 router / forced prefetch。Frontier 預設 auto，模型自己判斷是否用 FHIR、文獻或不用工具；只有使用者選「不使用病人資料」時移除 FHIR。這可避免把 Frontier 的正常自主能力降級成規則系統。


六、token 與 retry 原則

- 結構化摘要先用 1 個 API 產生所有分隔卡片。
- 每張卡獨立 parse 與 grounding validation。
- 只補送失敗卡，最多 2 張；成功卡不重做。
- 對可安全本地執行的 Chat compact tool 先執行，模型只做一次文字整理。
- 不建議固定把六張卡拆成兩次 3+3／3+2，因為 stateless endpoint 會重傳病人 context。
- partial parser 只保留完整可驗證片段，比再次發送 context 更省 token。


七、尚待產品決策（不阻塞本次程式碼）

1. 是否在 UI 中直接隱藏／標註 Nemotron 不支援結構化摘要與 Chat，或仍允許開發模式手動選擇。
2. 正式稽核要記錄哪些欄位與保存多久：模型、功能、簡體命中、grounding fail、retry 次數、token、latency、timeout、使用者是否重試；需先決定院內 log 與 PHI 政策。
3. 是否把「每模型每功能的最低通過率／P95 latency」做成部署 gate，例如摘要 >=95%、Chat >=95%、grounding failure 不能被渲染。
4. 自定義摘要需要再增加哪些科別 gold cases；目前四題偏重藥名、lab range 與 claim diagnosis。
