FHIR 健康摘要輸出穩定性優化說明
更新日期：2026-08-07

一、問題背景

地端模型 tvghbrain3.5 在產生跨院健康摘要時，過去需要自行選擇並依序呼叫疾病、目前用藥、檢驗結果等多個 FHIR 工具。

這種流程有幾個不穩定因素：

1. 模型可能沒有呼叫 FHIR 工具，直接要求使用者重新匯入資料。
2. 模型可能選錯工具、漏查其中一個資料領域，或產生不正確的 tool-call 格式。
3. 多次 API 往返增加逾時機率、延遲與 token 使用量。
4. 病歷包含大量重複領藥與歷史檢驗紀錄，會增加 context 大小並干擾小模型判斷。
5. 只靠加長 prompt，無法完全消除工具選擇、資料去重與格式錯誤。


二、主要調整方向

本次改善的核心，是將可以由程式確定處理的工作移出模型，讓模型只負責最後的白話文字整理。

調整後的流程：

使用者提問
  → 程式判斷是否屬於廣泛健康摘要
  → 在瀏覽器本地執行精簡 FHIR snapshot 工具
  → 程式完成篩選、去重及異常判定
  → 將一份精簡且結構化的結果送給模型
  → 模型產生臺灣繁體中文健康摘要
  → 完全沒有輸出時才有限重試一次


三、具體調整內容

1. 新增單一健康摘要工具

新增 getHealthSummarySnapshot，一次回傳：

- 疾病與診斷
- 目前用藥
- 最新異常檢驗
- 最近生命徵象

模型不再需要分別呼叫三至四個工具，因此減少工具選擇錯誤與 API 往返。


2. 由程式直接執行第一個工具

當問題明確要求整體健康摘要時，程式可以確定應使用 getHealthSummarySnapshot，因此不再先呼叫模型要求它選擇工具。

正常情況下，FHIR snapshot 在本地執行完成後，只需要一次模型請求產生最終回答。


3. 壓縮及去重 FHIR 資料

送進模型前會先執行以下處理：

- 疾病依名稱去重，保留最新紀錄。
- 藥物合併重複領藥紀錄。
- 目前用藥保留明確為 active 的項目，以及相對於病歷最新處方日的近 180 天處方。
- 同一檢驗項目只保留最新異常值。
- 排除 entered-in-error 的檢驗紀錄。
- 移除病人姓名、病歷號、醫師姓名等摘要不需要的識別欄位。

其中一份測試資料原本有 812 筆歷史處方，793 筆狀態為 completed。舊邏輯可能將歷史長期處方整理成 51 種「目前用藥」，調整後縮減為較合理的 31 種。


4. 提供結構化的 grounding 規則

Snapshot 會和資料一起提供以下規則：

- 只能根據本次提供的病歷紀錄回答。
- 不自行推測藥物成分、用途或治療目的。
- 檢驗是否異常以來源中的 interpretation 或已稽核參考範圍為準。
- 不自行加入一般正常值範圍。
- 資料已載入，不得要求使用者匯入或重新匯入。
- 使用臺灣繁體中文。
- 回答需涵蓋疾病、目前用藥及異常檢驗。
- 最後提醒使用者若有疑慮應與醫師討論。


5. 有限且有條件的重試

- 只有端點完全沒有產生任何文字時，才自動重試一次。
- 已開始產生文字後發生錯誤，不自動重送，避免重複答案與不必要的 token 消耗。
- 重試時不重新執行 FHIR 工具，只使用已整理好的 snapshot。
- 使用者停止或外層取消時，立即中斷等待。


6. 改善自動稽核判定

先前「是否要求重新匯入」的正則條件太寬，可能將「根據您匯入的資料」誤判成要求使用者再次匯入。

目前只攔截真正的操作要求，例如：

- 請重新匯入
- 需要先匯入
- 請點選或選擇匯入健康存摺


四、真實測試資料結果

- token 降幅：79.2%
- 原平均延遲：21,434 ms
- 優化後平均延遲：10,702 ms

病人資料 2：

五、穩定性改善的主要原因

穩定度提升並不是因為單純增加更多 prompt 限制，而是因為：

1. 工具選擇改由程式決定。
2. FHIR 資料先在本地完成篩選與去重。
3. 模型只收到回答問題需要的最小資料。
4. 正常流程只需要一次模型整理請求。
5. 對無輸出錯誤提供一次有限重試。
6. 對回答結構、語言及資料依據提供明確契約。

這種架構特別適合參數較小、tool calling 穩定性較弱的地端模型。


六、對話資料範圍與病人資料隔離

不再用持續膨脹的關鍵字／意圖規則決定所有模型是否能讀病歷，而是依模型能力採用不同控制方式。

Frontier 模型提供兩種模式：

1. 自動（預設）
   - 同時提供可用的 FHIR 與文獻工具，由模型依問題自行判斷要使用哪一項、兩者或都不用。
   - 不使用關鍵字縮減工具，也不由程式強制第一個工具。
   - 沒有載入病人時不提供 FHIR，只保留可用的文獻能力。

2. 不使用病人資料
   - 作為明確的隱私覆寫；永遠不提供 FHIR 工具。
   - 支援文獻工具時仍可搜尋最新指引。

地端／自訂小模型則提供明確範圍：

1. 一般醫學（不讀病歷）
   - 永遠不提供 FHIR 工具或「資料選擇」中的病歷快照。
   - 支援文獻工具的雲端模型仍可搜尋最新指引，但不會帶入病人資料。

2. 此病人資料
   - 可查詢目前載入病人的 FHIR 病歷。
   - 不提供外部文獻搜尋，避免把病歷問題和最新文獻來源混在一起。

3. 病人資料＋最新文獻
   - 同時允許 FHIR 與文獻搜尋。
   - 只在目前模型與連線確實支援文獻工具時開放。

「X 光有什麼問題嗎」在地端「此病人資料」模式會由精簡路由鎖定影像工具；在「一般醫學」模式不提供 FHIR。Frontier 的「自動」模式則保留完整可用工具，由模型自行判斷。

每則訊息都會保存當時的資料範圍。切換成一般醫學時，只會傳送同為一般醫學範圍的對話歷史，不會附帶先前的病人摘要；切回病人模式也不會把含外部文獻的回答帶入「只查病歷」模式。

地端標準聊天同樣遵守此邊界：一般醫學模式不會把病歷快照放進 system prompt。若問題要求「最新 guideline／目前更新」，但模型沒有文獻搜尋工具，模型必須明確說明無法驗證最新版本，不能將訓練知識宣稱為最新資訊。


七、Frontier 模型與地端模型的差異

地端小模型適合使用：

- 使用者明確選擇的資料範圍
- 較少且較小的工具 schema
- 程式預先執行可確定的工具
- 精簡、結構化的資料
- 明確輸出規則
- 有上限的失敗重試

Frontier 模型通常具備較好的工具選擇及多步推理能力，因此預設使用「自動」並保留完整可用工具，不要求使用者先選病歷或文獻；只有使用者明確選擇「不使用病人資料」時才移除 FHIR。地端小模型才套用明確範圍、工具 schema 縮減及預先執行。


八、測試範圍與限制

目前的 10/10 是自動化驗證結果，檢查內容包括：

- 是否使用正確的病人 FHIR 工具
- 是否包含疾病、用藥及檢驗區塊
- 是否包含與醫師討論的提醒
- 是否錯誤要求使用者重新匯入資料
- 是否產生非空白回答

此結果代表工具使用與回答結構穩定，不等同於每一個醫療敘述都已經過醫師人工審查。正式臨床使用仍應加入內容正確性、藥名、數值、時間範圍、來源一致性及繁簡體等更完整的稽核機制。
