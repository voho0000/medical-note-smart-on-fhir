# MediPrisma 前端效能基準

> 最近量測：2026-08-18｜版本基準：v0.48.0 working tree｜資料：內建虛構示範病人

本文件記錄臨床工作區常用操作的可重複效能基準。數字用來辨識後續改動是否造成退化，不代表所有電腦、瀏覽器或院內網路都會得到完全相同的結果。

「保守 p95」採五輪測試中最慢的一次 p95；「典型值」是五個單輪 p95 的中位數。這樣不會只挑最快的一輪當成基準。

另外兩項防退化指標：

| 指標 | 五輪觀察值 | 自動測試門檻 | 結果 |

主執行緒工作表列的是單次最長值，不是 p95，因此不與上方 p95 混用。17.1 ms 的典型捲動影格約略接近 60 Hz 畫面的 16.7 ms 影格預算；目前沒有秒級停頓，但仍值得持續追蹤。

## 量測情境

- macOS 26.6、Apple Silicon（arm64）
- Node.js 24.12.0
- Playwright 1.62.1、headless Desktop Chrome
- `next dev --turbopack`，本機 `localhost:3001`
- 先依序開啟病人資訊、就診紀錄、報告、用藥、文件完成暖機，再開始計時
- 載入中切換從臨床 tab 首次可見後點擊「就診紀錄」開始，到選取狀態與輕量載入畫面完成第一個 browser paint 為止；該分頁的重內容從下一個畫面週期掛載
- 分頁切換從點擊前開始計時，到分頁成為 active 並完成兩次 browser paint 為止
- 趨勢開啟從點擊檢驗名稱開始計時，到右側趨勢內容可見並完成兩次 browser paint 為止
- 趨勢關閉從點擊「關閉」開始計時，到右側趨勢隱藏並完成兩次 browser paint 為止；較重的圖表清理由下一個 paint 後執行
- 捲動測試在用藥清單 viewport 每個 animation frame 捲動 120 px
- Long Tasks API 用來觀察超過 50 ms 的主執行緒工作

## 自動防退化測試

測試檔：[`e2e/tests/workspace-performance.spec.ts`](../e2e/tests/workspace-performance.spec.ts)

單輪檢查：

```bash
npx playwright test e2e/tests/workspace-performance.spec.ts --project=chromium --workers=1
```

更新本機基準時連跑五輪：

```bash
npx playwright test e2e/tests/workspace-performance.spec.ts --project=chromium --workers=1 --repeat-each=5
```

每輪都會在 Playwright 結果附加 `performance-metrics` JSON，並在終端輸出同一份數據。CI 使用較寬鬆的上限，是為了容忍共享 runner 的波動，同時攔住秒級分頁卡頓、捲動嚴重掉幀與重複掛載 DOM 等明顯退化。

## 涵蓋與未涵蓋範圍

目前涵蓋：

- 已載入病人後的左側主分頁切換
- 累積報告檢驗趨勢的首次與後續右側開啟
- 右側檢驗趨勢關閉並返回既有功能面板
- 大型用藥清單捲動
- 重複切換後的 DOM 成長
- 操作期間的主執行緒長工作

目前未納入這組 p95：

- 第一次進站與冷啟動編譯
- 遠端 FHIR 載入、院內網路與 SMART OAuth
- AI 模型供應商的回應時間
- 低階院內電腦、iPad 與不同縮放比例的獨立基準

AI 產生時間受模型與網路影響，不應混入 UI p95。AI 摘要仍使用完整組裝後的臨床 context；相關完整性由摘要 use-case 與 generation hook 測試獨立保護，效能測試不以裁切輸入資料換取速度。

## 更新規則

1. 影響分頁掛載、虛擬清單、報告 pivot、clinical context 或 AI context 組裝的改動，應執行單輪效能測試。
2. 合併重大效能調整前，應執行五輪基準並更新本文件日期與數字。
3. 若本機 p95 變快但 CI 門檻未變，不需要為了漂亮數字縮緊門檻；先累積不同環境的穩定基準。
4. 若超過門檻，不應直接放寬上限，應先檢查是否發生重複掛載、同步大量運算、版面重排或非必要資料重建。
