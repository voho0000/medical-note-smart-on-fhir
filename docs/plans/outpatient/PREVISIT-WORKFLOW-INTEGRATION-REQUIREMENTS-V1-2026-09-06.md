# 醫析診前資料收集與系統整合需求文件

版本 v1.0　｜　日期 2026 年 9 月 6 日　｜　狀態 需求審閱版

提案脈絡：郭宜欣與鄭浩民之門診流程討論。審閱對象：臨床團隊、資訊室、醫析產品與開發團隊、系統維運單位。

## 1 目的與範圍

本案建立一套共用的診前資料流程，讓初診與固定門診病患能在家或到院後補充資料，並在看診時由醫析自動取得、呈現及供後續臨床功能使用。資料回存醫院資訊中台為整體架構的一部分，可在介面到位後接入。

交付目標是完成「建立任務、邀請填寫、身分配對、保存回答、醫護使用、院內交換」的完整交接。問卷內容、量表選擇、題目措辭、計分規則與疾病觸發條件另案討論，本文件不預設特定疾病或表單工具。

### 1.1 已確認的需求

- 初診與固定門診均須支援；第一階段共同基礎亦須驗證兩種情境。
- 居家填寫與現場填寫共用任務、回答格式與醫師端讀取流程。
- 問卷收集與中台正式入庫分開交付；中台尚未就緒不應阻擋已具備保存與讀取條件的醫析流程。
- 病歷取得時間影響個人化核對能力，不應成為一般填答的必要前提。
- 問卷結果要能在醫析中使用，不能只停留在另一個表單網站。

### 1.2 本次範圍與後續範圍

| 本次需求範圍 | 後續另行定義 |
| --- | --- |
| 啟動入口、任務生命週期、病人與門診配對 | 題目、量表、疾病別內容與授權 |
| 病患填答、暫存續填、代填及送出修訂 | 疾病條件式邀填與計分規則 |
| 跨裝置收件、醫析整合與醫護審閱 | 實際摘要版面及逐欄 CDSS 映射 |
| 資料保存、存取控制與院內交換 | 院方指定的正式中台資料規格 |
| 異常處理、驗收條件與導入依賴 | 各科臨床處置政策與服務時段 |

### 1.3 現有基礎與新增工作

醫析已有 FHIR 資料整合、民眾版摘要，以及把門診補值納入 CDSS 再計算的接點。目前門診生命徵象補值僅存在分頁記憶體；SMART 啟動設定使用讀取與搜尋範圍。這些能力可重用，但不等於已具備病患跨裝置送件或中台寫入能力。

本案須新增任務與填答服務、可持久保存的收件後端、身分及門診映射、醫析讀取與審閱紀錄，以及院內交換介面。院內模型連線可用，不代表中台介面與寫入權限已存在。既有草稿中的固定疾病試辦、表單工具及部署假設，均不作為本版已定案事項。

## 2 角色與完整作業流程

### 2.1 角色分工

| 角色 | 預期責任 | 邊界 |
| --- | --- | --- |
| 病患 | 核對填答對象、填寫、送出與必要修訂 | 只存取本人獲准的任務與資料 |
| 家屬或代填者 | 在允許範圍協助填答，留下代填身分與關係 | 代填權限與查看病歷權限分開 |
| 護理師或個管師 | 發起任務、現場協助、配對確認與待辦接手 | 實際負責角色與服務時段由門診指定 |
| 醫師 | 看診時查看、確認與使用相關結果 | 審閱行為對應明確的回答版本 |
| 醫析產品與開發團隊 | 任務流程、填答與醫師端整合、介面維護 | 不代替院方核發病歷寫入權限 |
| 院方資訊與維運單位 | 身分來源、網路、部署、中台介面與營運責任 | 系統間權限、監控與事件處理需定案 |

### 2.2 共用流程

1. 建立診前任務：由掛號、診前名單、報到、醫析或工作人員發起，取得唯一任務編號。
2. 提供入口：透過院方可用的通知管道、專屬 QR code 或院內平板進入；保留送達與失敗狀態。
3. 確認對象：驗證身分，確認本人或代填者，綁定病人及本次就診脈絡。
4. 填寫與續填：依任務載入固定版本內容；病歷可用時才提供個人化功能。
5. 正式送出：收件服務持久保存成功後，回覆收件編號、時間及版本；未完成者可保持部分填答狀態。
6. 醫析取用：醫師開啟病人後，自動取得對應任務、回答與歷次資料，呈現新資料及待確認事項。
7. 醫護審閱：記錄查看或確認的版本，必要時建立有負責人的待辦；依明確政策將適用資料供摘要或 CDSS 使用。
8. 院內交換：介面就緒後，按約定傳送指定資料，保存目的端識別碼及成功或失敗回覆。

流程主線：啟動入口 → 任務服務 → 病患填答 → 收件儲存 → 醫析查看與使用 → 院內交換 → 中台收件。

### 2.3 病歷可用時間與場景

初診與固定門診均適用下表。初診定義須保留科別／院所等脈絡及判定來源，不能因跨院資料找不到就診紀錄便直接判定為初診。

| 場景 | 當下可進行 | 後續銜接 |
| --- | --- | --- |
| 居家且無可用病歷 | 建立任務、驗證、一般填答與送出 | 到院或醫析取得病歷後合併使用 |
| 居家且已有可供使用的病歷 | 一般填答及獲准的個人化核對 | 看診時讀取確認與補充結果 |
| 現場且已取得病歷 | 同一流程，視條件加入個人化核對 | 送出後由醫師端取得最新版本 |
| 現場但尚無病歷或預約識別 | 建立任務與填答；必要時先待配對 | 配對確認後才納入指定病人的臨床視圖 |

## 3 任務與身分功能需求

本文件「必須」為驗收要求；「建議」為可替換技術方案；「待確認」不得當成已具備能力或既定政策。

### FR01 多入口啟動

必須提供同一套建立任務介面，供醫析及工作人員使用，並預留掛號事件、名單匯入或排程讀取的接法。沒有自動掛號介面時，仍可在授權工作站建立初診及固定門診任務。

### FR02 任務關聯與防重複

任務必須有獨立 taskId，並記錄院區、科別、就診情境及來源。病人使用院方識別系統與識別值的組合進行映射；同日多科或多次看診須可區分。不得以姓名或「病歷號加日期」作唯一配對鍵。重複事件或建立請求不得意外建立相同任務。

### FR03 身分驗證與待配對

病患端必須使用院方接受的驗證方式。無法確認身分或門診時，若允許先收件，資料須留在待配對區，不可自動進入某病人的摘要或 CDSS。人工配對須留下操作者、依據與時間；錯誤配對更正須撤銷舊關聯並通知已取用端重新整理。

### FR04 邀請憑證與權限

公共 QR code 只提供入口。專屬邀請使用具有效期限、可撤銷且不可猜測的憑證，並依操作配置驗證要求；URL 不得包含明文病歷號或病歷內容。允許填答不等於允許讀取既有病史。憑證過期後重新核發不得遺失已保存的回答。

### FR05 代填與共用裝置

必須區分病患本人、代填者及協助登錄的醫護人員，保存相應來源。代填可讀範圍與授權方式待院方定案。共用平板完成、退出或逾時後須結束任務存取，清除可見病患內容，下一位不得看到上一位的資料。

### FR06 改期取消與跨次使用

改期須更新預約關聯並保留歷程；是否重填或沿用，由後續內容有效期限規則決定。取消須停止後續提醒，保留回答並按保存政策處理。歷次回答不得悄悄改成另一場門診的本次回答；跨次使用必須標示原始時間與來源。

### FR07 通知與追蹤

通知管道依院方現有服務選用，不預設簡訊、LINE 或 App 已可用。須區分通知嘗試、送達或無法確認送達、填答與收件狀態。提醒頻率、停止條件、聯絡方式來源及負責單位須可配置，取消或不再適用的任務不得持續發送。

## 4 填答與臨床整合功能需求

### FR08 填答介面與暫存續填

填答須支援手機及院內平板，提供清楚的暫存、未保存、送出成功及失敗提示。重新驗證後可跨裝置續填。第一版不要求離線模式；斷線時不得假裝已保存，也不得在未核准的共用裝置長期保存病患資料。

### FR09 內容版本與送出完整性

任務必須指向可追溯的內容版本。既有作答途中不得被換成不同題意；如需遷移須明確通知並保留原版本。未填、不確定、不適用及明確否定必須可區分。伺服器依該版本校驗，依配置允許部分完成，不得把缺值當陰性或零分。

### FR10 修訂與併發處理

送出後修訂必須產生新回答版本，保留前一版本、修改時間及操作者。重複點擊或網路重送不得形成重複收件。兩台裝置同時編輯須偵測版本衝突，讓使用者確認後續處理，不得靜默覆蓋。

### FR11 病歷與 AI 的依賴隔離

一般收件不得依賴病歷或 AI 服務在線。個人化核對僅在資料可取得且具備適用權限時提供；須記錄病歷來源與時間。AI 不可用時仍可填寫、保存並查看原始回答；病歷後到時重新整合，不改寫病患原答。

### FR12 自動取得與更新

醫師開啟醫析病人脈絡時，系統必須查詢已確認配對的任務，優先對應本次門診，並可查看歷次結果。同日多任務須可識別，不明確時要求選定。新回答與修訂須可提示及重新取得；切換病人時必須清除前一病人的資料與請求結果。

### FR13 查看確認與待辦

必須分開記錄「已送出」「已查看」「已確認」與「中台已收件」。查看與確認對應 responseId 及 revision。已查看版本被修訂後，須顯示新版本尚未查看。待確認事項可指派負責人、記錄處理狀態；在家提前填寫的監看時段及交接方式須於上線前明確告知。

### FR14 摘要與 CDSS 使用

必須保留病患原答、系統衍生結果與醫護確認三種來源。摘要顯示時可回查原答；CDSS 只納入已有映射與使用政策的欄位，不將整份問卷直接當成已確認病歷。病患回報可先標示待確認或供允許的規則使用，與既有紀錄衝突時並列呈現，不自動覆蓋。

### FR15 衍生計算與快取更新

需計分或抽取的項目使用正式定義與版本，保留計算來源。答案修訂、配對更正或醫護確認異動後，受影響摘要與 CDSS 結果須失效並重新計算；尚未更新的結果必須可辨識，不得以舊結果標示為最新。

## 5 系統架構與部署選項

### 5.1 元件邊界

| 元件 | 主要責任 | 與既有醫析的關係 |
| --- | --- | --- |
| 任務與邀請服務 | 建立任務、關聯預約、發邀請及管理期限 | 新增後端，醫析可發起呼叫 |
| 病患填答介面 | 驗證後填寫、暫存、續填與送出 | 新增或串接既有表單工具 |
| 收件與資料服務 | 保存版本、來源、權限及稽核 | 新增正式持久化能力 |
| 醫析整合層 | 查詢、審閱、摘要及 CDSS 適用資料映射 | 延伸既有病人脈絡與臨床功能 |
| 院內交換程式 | 傳送、重送、對帳及回覆紀錄 | 依院方介面新增轉接層 |

表單平台可替換，但必須保留任務關聯、內容版本、原始回答及匯入狀態。Google、Microsoft、開源 renderer 或自建填答頁皆為候選，不在本版定案。不得把僅有姓名的試算表視為已完成身分串接。

### 5.2 部署方案比較

| 方案 | 病患端可達性 | 適用條件與限制 |
| --- | --- | --- |
| 院方對外入口搭配院內後端 | 在家及現場可用 | 院方已有或願意建立對外入口、驗證與受控交換通道 |
| 對外收件服務搭配院內主動拉取 | 在家及現場可用 | 收件環境經院方接受；院內允許向外建立驗證連線；需管理兩側副本 |
| 僅院內部署 | 僅可連院內服務的裝置 | 可驗證現場流程，不能宣稱完成居家填寫需求 |

建議先評估院方既有入口，其次評估院內主動拉取。主動拉取可避免要求外部直接連入院內服務，但仍依賴院方網路、驗證與維運配置，並非零資訊室依賴。對外收件服務的存放位置不預設為醫析既有 Firebase。

候選跨網路資料流：病患手機 → 對外收件服務；院內交換程式 → 向外拉取待接收資料 → 院內資料服務／中台；院內醫析 → 讀取院內資料服務。若選擇醫析直接讀取對外服務，須另確認院內可達性及存取權限。

### FR16 中台交換與收件確認

中台介面未就緒時，收件服務仍須能供醫析使用。交換介面需定義傳送原答、衍生資料或醫護確認資料的範圍，並保存目的端識別碼及處理回覆。HTTP 傳送成功不必然等於正式入庫成功，須以雙方約定的確認為準。

### FR17 重送與一致性

以任務、回答版本、目的端及操作識別建立冪等機制；逾時重試不得重複入庫。失敗須有可查原因、重試次數、人工接手與對帳方式。修訂、撤銷或配對更正須有對應交換行為，不得讓目的端永久保留未標示的錯誤版本。

## 6 資料契約與狀態

### 6.1 核心資料物件

下列為邏輯模型，欄位命名可在技術設計時調整。資料庫產品與 FHIR server 不在本版指定。

| 物件 | 最小資料內容 |
| --- | --- |
| 診前任務 | taskId、院區、科別、就診情境及來源、內容版本、狀態、建立時間 |
| 病人與門診關聯 | 身分命名空間與識別值、院內映射、appointmentId／encounterId 如有、配對狀態及確認紀錄 |
| 邀請與存取 | invitationId、任務關聯、期限、撤銷狀態、發送與驗證紀錄；憑證本體不寫一般日誌 |
| 回答版本 | responseId、revision、題目版本、逐題原答、完整性狀態、填答者及來源、保存與送出時間 |
| 衍生結果 | 原答版本、計算或映射版本、結果、產生時間及來源 |
| 審閱紀錄 | 回答版本、查看或確認者、時間、確認範圍及待辦 |
| 交換紀錄 | deliveryId、目的端、回答版本、傳送範圍、冪等識別、重試及收件回覆 |
| 稽核事件 | 操作者、角色、事件、對象識別、時間及結果；不複製整份病歷或回答 |

### 6.2 狀態必須分軸管理

| 狀態軸 | 建議狀態 | 轉換原則 |
| --- | --- | --- |
| 任務 | 已建立、開放填寫、已結束、已取消、已逾期 | 任務結束與資料刪除分開；重新開放須留下紀錄 |
| 配對 | 待確認、已確認、待更正 | 待確認不得進入指定病人的臨床結果 |
| 填答 | 未開始、草稿、部分送出、完整送出 | 修訂保留歷次正式送出版本 |
| 審閱 | 未查看、已查看、已確認 | 狀態綁回答版本，新版本重新標示 |
| 交換 | 未排程、待傳送、處理中、已收件、失敗、待人工處理 | 以目的端確認判定收件，不以發出請求判定 |

### 6.3 FHIR 對應原則

可用 Questionnaire 表達題目與版本、QuestionnaireResponse 表達回答與來源；已有 Encounter 才建立對應關聯。預約或任務尚未形成 Encounter 時保留本地關聯，不杜撰正式就醫紀錄。特定衍生結果可依接收端規格映射為 Observation 等資源，並保留原答可追溯性。

內部可先採版本化 JSON，再由轉接層輸出 FHIR。臨床確認狀態不能用 QuestionnaireResponse 的完成狀態代替。FHIR 版本、profile、代碼與接收端驗證條件須由交換契約定案，不把格式相符視為已取得寫入權限。

## 7 介面與非功能需求

### 7.1 必要介面能力

| 介面能力 | 請求要點 | 回覆與處理要求 |
| --- | --- | --- |
| 建立或更新任務 | 來源事件、病人／預約關聯、內容版本、冪等識別 | taskId、狀態、重複事件的既有結果 |
| 核發邀請與驗證存取 | 任務、使用者身分、用途及期限 | 限定範圍的存取；病史讀取另行授權 |
| 暫存與正式送出 | 題目版本、原答、預期修訂版本 | 持久保存結果、收件編號、版本或衝突回覆 |
| 醫析查詢 | 已驗證醫護脈絡、病人與門診關聯 | 對應任務、回答版本、審閱與更新狀態 |
| 查看確認與待辦 | 回答版本、操作者、確認範圍 | 不可混淆的審閱紀錄與待辦狀態 |
| 交換與收件回報 | 游標或指定版本、目的端、冪等識別 | 批次結果、目的端識別與錯誤；可安全重試 |

病人識別參數只用於查詢篩選，伺服器必須另驗證存取權限。各介面均須有明確版本、錯誤格式及可追蹤的 requestId；通知更新可採輪詢或事件推送，具體方案由部署環境選定。

### 7.2 非功能需求

- NFR01 存取邊界：伺服器驗證機構、角色、病人及任務權限；病患登入、醫護存取與系統交換使用各自的驗證及權限設定。
- NFR02 保存與稽核：正式送出只有在持久保存成功後回覆成功。傳輸與儲存採適用的加密；保存期限、備份、刪除及交換暫存清除政策須明確且可執行。
- NFR03 可用性與降級：AI、通知或中台故障不阻擋已可用的原答收件與查看；收件服務故障必須如實顯示，現場看診可繼續並有人工替代流程。
- NFR04 效能：量測填答保存延遲、送出至醫析可見延遲、查詢延遲及交換積壓。p95 目標、尖峰併發量、可用率、復原時間與可容忍資料損失，須依院方規模在上線前定案。
- NFR05 可操作性：手機、平板及桌面可閱讀操作，錯誤提示可理解，支援鍵盤與輔助技術的基本操作；共用裝置流程須實測。
- NFR06 維運責任：指定收件、中台交換、配對更正、資料恢復與臨床待辦的負責單位。監控記錄避免輸出憑證及完整病患內容。

## 8 分階段交付與驗收

### 8.1 交付順序

| 階段 | 交付內容 | 完成條件 |
| --- | --- | --- |
| A 共用基礎 | 任務、身分配對、保存版本、填答及醫析查看 | 初診與固定門診均可跑通；使用既有授權入口或人工發起 |
| B 入口串接 | 掛號／報到事件、診前通知、居家存取與現場續填 | 居家與現場均可用；重複事件、改期與取消可處理 |
| C 臨床功能深化 | 科別摘要、個人化核對、內容定案後的 CDSS 映射 | 依明確內容與資料使用政策驗收；原答可回查 |
| D 院內正式交換 | 中台格式轉換、收件確認、重送及更正 | 與院方完成端到端對帳與失敗演練 |

階段是能力交付順序，不是限制病患類型。B 與 D 的介面協調可提早進行；不必等 CDSS 全部成熟才啟動 A。A 使用院內限定環境時，只代表現場能力完成，整體居家需求仍待 B 完成。

### 8.2 功能驗收矩陣

| 編號 | 驗收場景 | 通過條件 | 需求 |
| --- | --- | --- | --- |
| AC01 | 初診與固定門診各完成一次流程 | 任務、收件、醫析查看均成功，資料來源與版本可回查 | FR01、12 |
| AC02 | 病歷未取得或 AI 離線 | 一般填答仍可送出並查看；個人化功能如實標示不可用 | FR11 |
| AC03 | 同名、跨院同號、同日多科 | 不自動錯配；無法確認者留待配對 | FR02、03 |
| AC04 | 公共 QR、轉傳連結、過期憑證 | 不洩露病史，不可越權操作，核發新憑證保留既有回答 | FR04 |
| AC05 | 代填與共用平板換人 | 來源可辨識，下一位無法讀取前一位資料 | FR05 |
| AC06 | 改期、取消及重複掛號事件 | 關聯可追溯，取消停止提醒，不重複建立任務 | FR02、06、07 |
| AC07 | 斷線、續填與兩裝置併發 | 保存提示正確，續填取回草稿，版本衝突可處理 | FR08、10 |
| AC08 | 部分填答及題目版本更新 | 缺值不當否定，原題意及內容版本可回查 | FR09 |
| AC09 | 醫師已查看後病患再修訂 | 新版本標示未查看，舊確認紀錄保留，衍生結果更新 | FR10、13、15 |
| AC10 | 醫析切換病人及來源衝突 | 不殘留上一位資料；原答與病歷並列，不靜默覆蓋 | FR12、14 |
| AC11 | 中台逾時、重送及正式回覆 | 不重複入庫，成功狀態以接收端確認為準 | FR16、17 |
| AC12 | 已交換資料修訂或配對更正 | 舊關聯撤銷／更正可追蹤，醫析與目的端可辨識新版本 | FR03、15、17 |

### 8.3 營運驗證

邀請率、完成率、填寫與協助時間、看診前可取得率、醫師查看率及待辦處理時間，須分別觀察初診／固定門診、居家／現場。分母及排除條件須先定義，不能只以送出份數判定成功。量化目標由臨床團隊與維運單位在試行前確認，不在本版杜撰。
