## 1. 定義與立場

### 1.1 什麼叫 agentic 門診系統

不是「AI 自己看診」。定義如下：

> 系統在**看診前後**主動替醫療團隊把可以先做的事做完（整理資料、產生摘要、發問卷、擬草稿、排待辦），在**看診中**把結果與草稿放到醫師面前，**人只做簽核與修改**；每一個動作都有規則框住、有稽核紀錄、可以一鍵關掉。

三條紅線，寫進所有申請與設計文件：

1. **無自主行動**：agent 不寫回正式病歷、不開立醫囑、不通知病人臨床結論；只產生草稿與待辦，由人簽核後才生效。
2. **受限任務**：只做資料整理、摘要、問卷、草稿、提醒；不做診斷、分流、用藥決定。
3. **可稽核、可關閉**：每個動作記錄輸入來源、模型與規則版本、簽核者；有配額與總開關。

這個定位對應衛福部 2026-05-29 生成式 AI 指引對「AI Agent System」的排除範圍：本系統是**輔助型 agent**，不是自主 agent。

### 1.2 為什麼是基礎設施問題，不是模型問題

現行系統是**即時、單次、無狀態**：醫師打開病人，系統當場算一次，關掉就沒了。Agentic 的差別在於系統要能**在沒有人打開畫面時**工作、要**記得**自己做過什麼、要**知道**外面發生了什麼。這三件事都不是模型能給的，是基礎設施。

## 3. 八層基礎設施

每層列：目的、必須具備、現況、缺口、階段。「現況」以本中心醫析平台為基準。

### 3.1 事件層：系統要知道發生了什麼

| 項目 | 內容 |
|---|---|
| 目的 | 讓 agent 在對的時間動起來，而不是等人打開畫面 |
| 必須具備 | 掛號、改期、報到、檢驗回報、影像／心超／病理報告簽核、開藥、出院這些事件能被訂閱（FHIR Subscription、訊息佇列或 webhook 皆可）；每個事件帶病人、就診、時間、來源 |
| 現況 | 無。HIS 不對外發事件 |
| 缺口 | 全部。最低需求是**明日門診名單**（批次）與**報到事件**（即時）兩項 |
| 階段 | Phase 0 用名單批次；Phase 1 要報到與報告簽核事件；對應衛福部 FHIR Box 的訂閱能力 |

沒有事件層，agent 只能做「前一晚批次」。這反而是好的起點（見 §5）。

### 3.2 資料層：一個可讀可寫的 FHIR 面

| 項目 | 內容 |
|---|---|
| 目的 | 所有 agent 讀寫都走同一個標準面，不直接碰 HIS 資料表 |
| 必須具備 | (a) 跨院讀取：健保雲端資料；(b) 院內讀取：門診紀錄、住院病摘、癌登、護理紀錄、自費項目；(c) **寫入路徑**：QuestionnaireResponse、草稿文件（DocumentReference 標 draft）、待辦（Task）、Provenance；(d) 病人自填資料的持久化 store；(e) 批次查詢（明日門診名單的所有病人） |
| 現況 | (a) 已有，經雲端橋接與醫雲啟動；(b)(c)(d)(e) 無。門診補值只存分頁記憶體 |
| 缺口 | 寫入是零；自填 store 是第一個要新建的資料庫 |
| 階段 | Phase 0 自填 store（院內網）；Phase 1 草稿與 Task 寫入；Phase 2 院內讀取面；Phase 3 中台正式入庫 |

**Provenance 是硬規則**：每一筆 agent 寫入的資源都掛 Provenance，記 agent 身分、模型版本、規則版本、輸入資源清單、簽核者。沒有 Provenance 的寫入視為無效。

### 3.3 術語層：跨院命名的統一服務

| 項目 | 內容 |
|---|---|
| 目的 | 規則層要能判斷「這個值是 NT-proBNP」「這是心超」，不能靠字串猜 |
| 必須具備 | 院級 terminology service：LOINC、SNOMED CT、ICD-10-CM、健保醫令碼、院內碼之間的對應；版本化；查詢 API；未對應項目的回報流程 |
| 現況 | app 內別名表（canonical key＋多變體文字比對），能用但只在一個 app 裡 |
| 缺口 | 院級服務、版本管理、跨系統共用 |
| 階段 | Phase 1 把現有別名表升格為獨立服務；Phase 2 接院內碼 |

這一層最不起眼，卻是實務上最常見的阻塞點：跨院檢驗、檢查、藥品名稱很雜，每新增一科就撞一次。

### 3.4 身分與授權層：agent 要有自己的身分

| 項目 | 內容 |
|---|---|
| 目的 | 知道是誰在讀、誰在寫、代誰行事、病人同意到哪 |
| 必須具備 | (a) 病人身分：預約 token、平板 launch 脈絡、行動身分；弱綁定（末四碼＋生日）禁用；(b) 醫事人員：SSO＋科別、次專科、角色；(c) **agent 身分**：獨立的 SMART on FHIR client，有自己的 scope，代理使用者行事，不借用醫師帳號；(d) 同意登錄簿：病人授權哪些資料類型給 agent、能否上雲、代填者關係；(e) 代填與共用裝置：每次填完自動結束 session |
| 現況 | 醫師登入與平板 launch 已有；其餘無 |
| 缺口 | agent 身分、預約 token、同意登錄簿 |
| 階段 | Phase 0 平板 launch；Phase 1 預約 token 與同意登錄；Phase 2 agent 獨立 client |

對應衛福部「健康資料空間」的病人授權構想：病人可排除特定紀錄類型。同意登錄簿要從一開始就能表達這件事。

### 3.5 規則層：確定性先於模型

| 項目 | 內容 |
|---|---|
| 目的 | 決定 agent「能不能做」；模型只負責「怎麼寫」 |
| 必須具備 | 版本化規則庫（何時發問卷、何時升級急性訊號、哪些資料進摘要、哪些用藥組合警示、時效窗）；規則以 CQL 或等價的宣告式格式表達；每條規則有測試案例與觸發計數器；規則變更走審查 |
| 現況 | 個人化指引 pack（宣告式、有 fixture）與「防線紀律」（每條防線要有計數器，沒觸發就刪）已是雛形 |
| 缺口 | CQL 化、院級版本管理、與衛福部「健康規則空間」對接 |
| 階段 | Phase 0 沿用 pack；Phase 2 評估 CQL 執行引擎 |

規則層的設計原則：**能用確定性規則解決的，不用模型**。模型錯誤不靠加防線解，只有「模型無關、系統有特權知識、不加會無聲出錯」三條件全中才寫規則。

### 3.6 模型與工具層：gateway、註冊表、評測

| 項目 | 內容 |
|---|---|
| 目的 | 讓 agent 安全地呼叫模型與工具，且可以被量測 |
| 必須具備 | (a) 模型 gateway：地端與雲端、PII 脫敏、配額、context 上限；(b) **工具註冊表**：agent 能呼叫的每個工具（FHIR 查詢、計算器、問卷發放、草稿建立、待辦建立）有定義、權限、稽核；(c) prompt 與 skill 版本管理；(d) **離線評測**：固定 fixture、LLM judge 與確定性測試並用、每次改動記錄前後數字；(e) 模型註冊表：可用模型、成本、延遲、適用任務 |
| 現況 | (a) 已有地端與雲端 gateway、PII 脫敏；(c) 有範本庫；(d) 有摘要與用藥整合的評測雛形；(e) 有模型註冊 |
| 缺口 | 工具註冊表與權限；評測資料集規模化；工具呼叫的稽核 |
| 階段 | Phase 0 工具註冊表（讀取類）；Phase 1 寫入類工具＋稽核 |

工具是 agent 的手。手要先有清單、有權限，才談自動化。

### 3.7 執行層：任務佇列、狀態機、簽核、稽核帳

這是 agentic 的心臟，也是現在完全沒有的一層。

| 項目 | 內容 |
|---|---|
| 目的 | 讓系統在沒有人打開畫面時工作，並記得自己做過什麼 |
| 必須具備 | (a) 任務佇列：批次（前一晚）與事件觸發（報到）兩種入口；重試、去重、逾時；(b) **就診狀態機**（見下）；(c) 簽核流程：草稿 → 醫師採納／修改／駁回 → 生效；駁回原因回饋評測；(d) **稽核帳**：不可改、append-only，每筆記 agent 身分、任務、輸入資源清單、模型與規則版本、輸出、簽核者與時間；(e) 配額與總開關：每科、每日、每病人；一鍵停用 |
| 現況 | 無 |
| 缺口 | 全部 |
| 階段 | Phase 0 批次佇列＋稽核帳；Phase 1 狀態機＋簽核；Phase 2 事件觸發 |

就診狀態機：

```
 名單產生 ──► 診前批次 ──► 邀請已送 ──► 已填答 ──► 已報到 ──► 診中 ──► 已簽核 ──► 診後追蹤 ──► 結案
              │ 科別摘要草稿                │ 補現場資料      │ 醫師採納/     │ 待辦到期
              │ 問卷邀請                    │ 摘要更新        │ 修改/駁回     │ 監測提醒
              │ 用藥整合草稿                │                 │               │
              └ 待辦初稿                    └ 急性升級 ───► 護理站
```

每個狀態轉移是一筆稽核帳；agent 動作只發生在「診前批次」「已報到」「診後追蹤」三個狀態，「診中」與「已簽核」只有人能推進。

稽核帳一筆的最小欄位：

```
{ task_id, visit_id, patient_ref, state_from, state_to,
  actor: {type: agent|human, id, on_behalf_of},
  inputs: [resource refs], model: {id, version}, rules: [{id, version}],
  output_ref, decision: null|accepted|modified|rejected, reason, timestamp }
```

### 3.8 觀測與治理層

| 項目 | 內容 |
|---|---|
| 目的 | 知道系統有沒有用、有沒有壞、有沒有越線 |
| 必須具備 | (a) 線上指標：醫師閱讀率、草稿採納率、修改率、駁回率、每條防線觸發計數、延遲、成本；(b) 漂移監控：模型或資料分布變化的警示；(c) 事件通報：錯誤草稿被簽核後的處理流程；(d) 政策：PHI 保存位置與期限、同意、雲端供應商資料處理協議、跨境；(e) 法規：衛福部指引定位、醫材邊界、IRB、日後送互通認證實驗室 |
| 現況 | (a) 有行為事件（GA4）與 AI 結果事件；(d)(e) 部分文件化 |
| 缺口 | 採納率與駁回率（要先有簽核流程）、漂移、事件通報 |
| 階段 | 與執行層同步 |

## 5. 建議順序：從「前一晚批次 agent」開始

### 5.1 為什麼先做批次

- 不需要事件層，只要明日門診名單。
- 不需要即時性，延遲與成本都可控，地端模型跑得動。
- 法規最乾淨：所有產出都是草稿，隔天醫師簽核，沒有任何自主行動。
- 一次立起執行層的三個核心：任務佇列、稽核帳、簽核流程。

### 5.2 Phase 0 批次 agent 的工作清單

前一晚對每位明日門診病人：

1. 取得跨院資料，產生**科別摘要草稿**（四層骨架）。
2. 依科別、初複診、規則層決定要發哪些問卷，建立**問卷邀請**（報到後平板填）。
3. 產生**用藥整合草稿**。
4. 把規則層判出的缺口（該做未做的檢查、時效過期的指標）寫成**待辦初稿**。
5. 全部寫進稽核帳；隔天醫師開病人時看到草稿與「採納／修改／駁回」。

### 5.3 分階段

| 階段 | 新增能力 | 需要的基礎設施 | 對資訊室的依賴 |
|---|---|---|---|
| Phase 0 | 前一晚批次、報到後平板問卷、簽核、稽核帳 | 執行層（批次）、自填 store（院內網）、工具註冊表（讀取類） | 明日門診名單匯出 |
| Phase 1 | 報到觸發更新、居家問卷、草稿與待辦寫入 | 事件層（報到）、預約 token、寫入路徑、同意登錄 | 報到事件、預約通知帶連結、對外入口或 DMZ |
| Phase 2 | 報告簽核觸發、多科擴充、agent 獨立身分 | 事件層（簽核）、術語服務、agent SMART client | 報告簽核事件、院內讀取面、科別參數 |
| Phase 3 | 正式入庫、規則空間對接、認證 | 中台介面、CQL 引擎 | 中台規格、認證實驗室 |

## 6. 風險

| 風險 | 影響 | 對策 |
|---|---|---|
| 沒有事件層，agent 永遠只能批次 | 診中無法更新 | 批次已有價值；事件層列為對資訊室的第一項要求 |
| 寫入路徑開了，錯誤草稿被簽核 | 病安 | 草稿標示、Provenance、駁回回饋評測、事件通報流程 |
| agent 借醫師帳號跑 | 稽核失真、權限過大 | Phase 2 前就設計獨立 client；Phase 0 稽核帳先記「代誰行事」 |
| 術語對應錯 | 規則誤判 | 未對應項目回報流程；規則只吃 canonical key |
| 模型漂移或供應商變動 | 品質下滑 | 離線評測每次改動跑；模型註冊表可切換 |
| 自主行動的期待被放大 | 法規與信任 | 三條紅線寫進每份文件；總開關 |
| 全部由一個中心蓋 | 單點、不可持續 | 八層拆清楚，能交給資訊室與國家 FHIR Box 的就交出去 |
